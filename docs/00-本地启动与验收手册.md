# 本地启动与验收手册

> 适用版本：M1 完成态
> 目标：Docker Desktop 装好后 **5 分钟**把「中间件 → 后端 → 前端」跑起来，并按 §8 逐项验收
> 环境：Windows 10/11 · JDK 21 · Maven 3.9+ · Node 20+

---

## 0. 先明确两件事

**① 本轮只需要两个容器：`postgres`、`redis`**

MinIO 要等 M6「代码包上传」才用得上；`embedding`（BGE-M3）是 M3 语义审查才需要的，首次启动要下 2.2GB 模型、健康检查预热给了 300 秒。
**不要一上来 `up -d` 全部**——光等模型下载就半小时，然后你会以为是自己配错了。

**② `deploy/.env` 是给 Docker Compose 读的，不是给 Spring Boot 读的**

这是最容易踩的坑：改完 `.env` 里的 `DB_PORT`，重启后端发现还连 5432 —— 因为后端读的是**操作系统环境变量**，`.env` 文件对它完全无效。

默认值两边是对齐的（`codereview / codereview @ localhost:5432`），所以**什么都不配也能起来**。只有改端口或改密码时，才需要把同样的值 export 到系统环境变量。

## 2. 安装 Docker Desktop（一次性，15–30 分钟）

只在第一次做，之后不用再管。

1. **BIOS 开虚拟化**：任务管理器 → 性能 → CPU → 右下角「虚拟化：已启用」。没开就进 BIOS 打开 VT-x / SVM。
2. **装 WSL2**（管理员 PowerShell）：
   ```powershell
   wsl --install
   ```
   装完重启，`wsl -l -v` 能看到 `docker-desktop` 即正常。
3. **装 Docker Desktop**：官网下载 `Docker Desktop Installer.exe`，安装时勾选 **Use WSL 2 instead of Hyper-V**。
4. 启动 Docker Desktop，等左下角鲸鱼图标**变绿且不再转圈**（首次初始化约 2 分钟）。
5. 验证：
   ```powershell
   docker version        # 必须同时有 Client 和 Server 两段
   docker run --rm hello-world
   ```

**常见坑**

| 现象 | 处理 |
|---|---|
| `docker version` 只有 Client，Server 报错 | Docker Desktop 没启动 / WSL2 未装好 |
| 与 VMware、VirtualBox 冲突 | 新版用 WSL2 后端基本无碍；老版 VirtualBox 需升级到 7.x |
| 拉镜像卡住 | Docker Desktop → Settings → Resources → Proxies 配公司代理 |
| 磁盘不足 | 镜像 + 卷约需 15GB，`docker system df` 可查占用 |

## 3. 生成两个密钥并写进 `deploy/.env`（1 分钟）

```powershell
# 生成 32 字节随机密钥（Base64，44 字符）。跑两次，一次给 JWT，一次给凭据加密
$b = New-Object byte[] 32
[Security.Cryptography.RandomNumberGenerator]::Create().GetBytes($b)
[Convert]::ToBase64String($b)
```

Git Bash 里等价写法：`openssl rand -base64 32`

```powershell
Copy-Item deploy\.env.example deploy\.env
notepad deploy\.env
```

真正需要动的只有三行：

| 变量 | 填什么 | 不填的后果 |
|---|---|---|
| `APP_JWT_SECRET` | 第一串密钥 | 回退到源码里的 dev 默认密钥：**能跑，但任何人都能伪造管理员令牌** |
| `APP_REPO_SECRET_KEY` | 第二串密钥 | 后端正常启动，但「Git 凭据」功能禁用，只能接公开仓库 |
| `APP_ADMIN_PASSWORD` | 自定强密码 | 默认 `Admin@123456`，启动日志会打黄色告警 |
| `DEEPSEEK_API_KEY` | DeepSeek 控制台申请的 `sk-` 密钥 | 语义审查（M3）不可用，只能跑静态分析 |

⚠️ 两个密钥的格式要求**不一样**：JWT 只要 Base64 解码后 ≥ 32 字节即可；凭据密钥必须**正好** 32 字节。上面两条命令生成的两串都满足。

> 凭据密钥丢失 = 已录入的私有仓库令牌全部无法解密，只能重新录入。这是与数据库分离保存的代价，答辩时可以讲。

## 4. 启动中间件（1 分钟，首次含镜像拉取）

```powershell
docker compose --env-file deploy\.env -f deploy\docker-compose.dev.yml up -d postgres redis
docker compose --env-file deploy\.env -f deploy\docker-compose.dev.yml ps
```

期望输出：

```
NAME          IMAGE                     SERVICE    STATUS
cr-postgres   pgvector/pgvector:pg16    postgres   Up (healthy)
cr-redis      redis:7.4-alpine          redis      Up (healthy)
```

`starting` → `healthy` 约 10 秒。日志确认：`docker compose -f deploy\docker-compose.dev.yml logs --tail=20 postgres`，应出现 `database system is ready to accept connections`。

顺手确认镜像真的带 pgvector（这一步查的是**镜像能力**，扩展本身由 Flyway 迁移时创建）：

```powershell
docker exec cr-postgres psql -U codereview -d codereview -c "select name, default_version from pg_available_extensions where name='vector'"
```

有行返回即可。返回空说明用错了镜像，见 §10。

## 6. 冒烟验收（2 分钟）

### 6.1 未认证必须被拒

```powershell
curl.exe -s -i http://localhost:8080/api/users | Select-String -Pattern "HTTP/|code"
```

或直接看浏览器：http://localhost:8080/api/users

期望 `401`，响应体含 `"code":40100`、`"traceId":"..."`。

### 6.2 登录并拿令牌

```powershell
$r = Invoke-RestMethod -Method Post http://localhost:8080/api/auth/login `
     -ContentType 'application/json' `
     -Body '{"username":"admin","password":"Admin@123456"}'

$r.code                                    # 0
$r.data.user.roles                         # ADMIN
$r.data.user.permissions.Count             # 权限点总数（种子全量授予 ADMIN）
$r.data.user.passwordResetRequired         # False
$token = $r.data.accessToken
```

必须同时满足两点，否则是设计被改坏了：

- 响应体里**没有** refreshToken —— 刷新令牌只走 `Set-Cookie: refresh_token=...; Path=/api/auth; HttpOnly; SameSite=Lax`
- 响应体里**没有** password 字段

### 6.3 带令牌访问受保护接口

```powershell
$u = Invoke-RestMethod "http://localhost:8080/api/users?page=1&pageSize=10" -Headers @{ Authorization = "Bearer $token" }
$u.data.records.Count      # >= 1
$u.data.records[0]         # 不应出现 password 字段
```

### 6.4 权限点真的生效（这条最能说明问题）

1. 用 admin 在「用户管理」建一个账号，只分配 `DEVELOPER` 角色；
2. 退出，用该账号登录，访问 http://localhost:8080/api/users 。

期望 `403` + `"code":40301`。因为鉴权按**权限点**而不是角色名，缺 `system:user:list` 就被拦。

### 6.5 接口文档

http://localhost:8080/api/swagger-ui.html 能打开，`01-认证` / `系统管理` / `项目管理` 分组齐全。

## 8.5 M2 验收：跑通一条真实审查链路

环境就绪后，用**本项目自己的仓库**当审查对象，5 分钟走完「接入 → 同步 → 审查 → 报告」。

### 8.5.1 接入并同步仓库

```powershell
$base = 'http://localhost:8080/api'
$login = Invoke-RestMethod -Method Post "$base/auth/login" -ContentType 'application/json' `
  -Body '{"username":"admin","password":"Admin@123456"}'
$h = @{ Authorization = "Bearer $($login.data.accessToken)" }

$body = @{ name='智能代码审查系统'; code='ai-codereview'; language='JAVA';
           repoUrl='https://github.com/Zephyr-2026-cn/Code-Review-System.git'; repoBranch='main' } | ConvertTo-Json
$proj = Invoke-RestMethod -Method Post "$base/projects" -Headers $h -ContentType 'application/json' -Body $body
$proj.data.syncStatus   # UNBOUND → CLONING → READY（每 5 秒查一次 GET /projects/{id}）
```

同步完成后 `GET /projects/{id}` 应返回 `syncStatus=READY` 与非空的 `lastCommitId`。
克隆在后台线程执行，接口本身只做入库与状态抢占。

### 8.5.2 发起审查并观察状态

```powershell
$task = Invoke-RestMethod -Method Post "$base/tasks" -Headers $h -ContentType 'application/json' `
  -Body '{"projectId":1,"reviewMode":"FULL"}'
$task.data.status   # QUEUED

$t = Invoke-RestMethod "$base/tasks/$($task.data.id)" -Headers $h
$t.data.status; $t.data.issueCount; $t.data.stats
```

期望：状态沿 `QUEUED → FETCHING → SLICING → ANALYZING → FUSING → DONE` 推进，
`stats` 里能看到 `filesTotal / filesAnalyzed / analyzeMs / enginesDetail`。

### 8.5.3 看报告

```powershell
$r = Invoke-RestMethod "$base/tasks/1/report" -Headers $h
$r.data.summary.bySeverity
$r.data.summary.byCategory
$r.data.issues | Select-Object -First 5 severity, filePath, startLine, title
```

| 验收点 | 通过标准 |
|---|---|
| 文件清单 | `summary.scannedFiles` 与仓库中 `.java` 数量一致（排除 test/target） |
| 缺陷定位 | 每条缺陷都有 `filePath:startLine`，且该行确实对得上规则描述 |
| 类别完整 | `byCategory` 中不出现空值（说明 `rule_category_map` 覆盖了规则集） |
| 来源统计 | `bySource.STATIC` 等于缺陷总数（M2 阶段尚无 LLM） |
| 耗时合理 | 百级文件的项目在 10 秒内完成 |

### 8.5.4 边界验收（这四条最能体现工程完整性）

| 场景 | 操作 | 期望 |
|---|---|---|
| 重复提交 | 同一项目连续发起两次审查 | 第二次 `409 / 40903`「该提交已有正在进行的审查任务」 |
| 运行中取消 | 任务处于 ANALYZING 时 `POST /tasks/{id}/cancel` | 返回仍在途，数秒后变 `CANCELED`，`issueCount=0` |
| 增量模式 | `reviewMode=INCREMENTAL` | `400 / 40001`「增量审查计划在 M4 提供」 |
| 仓库未同步 | 对 `syncStatus != READY` 的项目发起审查 | `409 / 40903`「项目仓库尚未同步完成」 |

> 增量模式已在 M3 实现，上表那一行是 M2 时期的行为。现在应改为：未传 `baseCommit` 时返回
> `400 / 40001`「增量审查必须指定基线提交」；基线等于 HEAD 时返回「没有可审查的变更」。

### 8.5.5 队列与 worker 自检

```powershell
docker exec cr-redis redis-cli XINFO GROUPS review:queue   # consumers=2, pending=0
docker exec cr-redis redis-cli XLEN review:queue
```

后端日志里应能看到 `审查 worker 已启动: 并发=2` 与 `已创建审查队列消费者组`。
`pending` 长期不为 0 说明 worker 卡住或 ack 失败，先查日志里有无 `消息 ack 失败`。

## 8.6 M3 验收：语义审查 + 双路融合 + 增量切片

### 8.6.1 前置：配置大模型密钥

语义审查按 token 计费，密钥只走环境变量，**不写进配置文件、不提交仓库**：

```powershell
# 当前会话生效（重开终端失效）
$env:DEEPSEEK_API_KEY = "sk-..."
# 永久生效（新开终端仍可用）
[Environment]::SetEnvironmentVariable("DEEPSEEK_API_KEY", "sk-...", "User")
```

重启后端，日志应出现：

```
语义审查引擎就绪: model=deepseek-chat, baseUrl=https://api.deepseek.com, 并发=4, 单任务文件上限=40
```

没配密钥不会导致启动失败，只会打印 `语义审查引擎已启用但未配置 DEEPSEEK_API_KEY`，
任务照常跑静态分析，语义部分为空。

### 8.6.2 全量 + 双引擎

```powershell
$t = Invoke-RestMethod -Method Post -Uri "http://localhost:8080/api/tasks" `
  -Headers @{ Authorization = "Bearer $token" } -ContentType "application/json" `
  -Body '{"projectId":1,"reviewMode":"FULL","engineFlags":{"pmd":true,"llm":true}}'
```

期望（本机 93 个 Java 文件实测）：

| 指标 | 参考值 |
|---|---|
| 状态 | `PARTIAL`（语义审查只送审前 40 个文件，属预期截断） |
| 静态缺陷 | 89 条 |
| 语义缺陷 | 11~27 条（模型非确定性，条数会浮动） |
| 语义耗时 | 14~18s（4 并发、10 个请求） |
| `stats.warnings` | 只应出现「语义审查文件数超上限 40」，**不应出现「分析超时」** |

页面「可信度构成」卡片会显示 `双引擎印证 / 语义独有 / 静态独有` 三项条数。

### 8.6.3 增量切片

```powershell
# ① 先看有哪些基线可选
Invoke-RestMethod "http://localhost:8080/api/projects/1/commits?limit=10" -Headers $headers

# ② 选一个比 HEAD 早的提交作为基线
$body = '{"projectId":1,"reviewMode":"INCREMENTAL","baseCommit":"<完整 sha>","engineFlags":{"pmd":true,"llm":true}}'
```

期望：`filesTotal` 等于两次提交之间的源码变更数（而非全仓文件数），
`review_task_file` 里的 `change_type` 为 `ADDED / MODIFIED / RENAMED`，
`additions / deletions` 是真实行数。

### 8.6.4 三道边界（体现工程完整性）

| 场景 | 期望 |
|---|---|
| 增量不传 `baseCommit` | `400 / 40001`「增量审查必须指定基线提交」 |
| 基线等于当前 HEAD | `400 / 40001`「基线提交与当前 HEAD 相同，没有可审查的变更」 |
| 基线在本地不存在 | `400 / 40001`「仓库中找不到基线提交 …，请先同步仓库」 |
| 密钥没配却开了 `llm` | 任务正常完成，`engineErrors` 里写明「未配置 DEEPSEEK_API_KEY」 |

### 8.6.5 反幻觉自检

语义结果必须能通过**引用核对**：模型要照抄被举报的源码行，服务端拿它比对真实文件，
对不上直接丢弃。验证方式——查任一语义缺陷的 `evidence`：

```sql
SELECT rule_id, evidence->>'quoteVerified' FROM review_issue WHERE source = 'LLM' LIMIT 5;
```

`quoteVerified` 全为 `true` 说明这条链路在生效。

## 8.7 M4 验收：审查报告页

报告页是演示核心，验收重点不是"能打开"，而是"点一条缺陷能不能把证据讲清楚"。

### 8.7.1 页面结构

打开 `http://localhost:5173/tasks/{id}`，页面分三块：

| 区域 | 内容 | 验收点 |
|---|---|---|
| 顶部 | 任务号、状态、模式、**结论徽标** | 徽标显示「阻断 / 高风险 / 需关注 / 通过」，鼠标悬停给出判定理由 |
| 左栏 | 按文件分组的缺陷树 | 组头有文件级最严重色点与条数；点击可折叠；顶部可按严重度筛选、按关键字搜索 |
| 右栏 | 代码 + 双引擎证据 | 代码自动滚到缺陷行并高亮；下方两张卡片分别是静态规则与大模型的原始表述；再下方是修复建议 |

### 8.7.2 逐项打勾

| # | 操作 | 期望 |
|---|---|---|
| 1 | 打开任一已完成任务 | 右侧默认选中第一条缺陷，代码面板已滚动到该行并高亮 |
| 2 | 点另一条缺陷 | 代码重新定位；「上一条 / 下一条」按钮可连续翻阅，翻到首尾时按钮置灰 |
| 3 | 看「可信度构成」 | 显示「双引擎印证 / 语义独有 / 静态独有」三档计数，与库中 `flag` 分布一致 |
| 4 | 打开一条 `STATIC_ONLY` | 静态卡片有内容，大模型卡片显示「本次未命中」 |
| 5 | 打开一条 `LLM_ONLY` | 大模型卡片有内容并显示模型名，静态卡片「本次未命中」 |
| 6 | 打开增量任务的缺陷，切「差异」 | 显示新增行绿底、删除行红底、双列行号；冲突行有黄色左边条 |
| 7 | 缺陷行不在本次改动内时切「差异」 | 顶部出现「该文件本次提交未修改缺陷所在行」提示，不静默跳到别处 |
| 8 | 把浏览器拉窄到 600px 以下 | 侧边栏自动收成图标栏，主体变单列（问题树在上、代码在下） |

### 8.7.3 接口自检

```bash
T=$(curl -s -X POST http://localhost:8080/api/auth/login -H 'Content-Type: application/json' \
     -d '{"username":"admin","password":"Admin@123456"}' | sed -n 's/.*"accessToken":"\([^"]*\)".*/\1/p')
curl -s -H "Authorization: Bearer $T" "http://localhost:8080/api/issues/1/context?contextLines=10" | head -c 600
```

期望：返回 `issue`、`lines`（带行号）、`evidence`；增量任务的缺陷额外带 `diff`。
`notice` 有值表示代码没能加载（文件已删、路径越界、文件过大），此时接口仍是 **200**，
页面降级展示缺陷描述而不是整页报错——这是刻意设计，不是失败。

### 8.7.4 三条边界

| 场景 | 期望 |
|---|---|
| 缺陷路径被篡改为 `../../etc/passwd` | `lines` 为空，`notice` 提示路径不合法，不读仓库外文件 |
| 缺陷所在文件已从工作目录删除 | `notice` 提示「已不在工作目录中」，其余字段正常 |
| 同步仓库后文件被改短，缺陷行号超出文件行数 | 展示文件尾部并提示「行号超出文件当前行数」 |

### 8.7.5 关于「双引擎印证为 0」

这不是缺陷。印证要求**同文件 + 同类别 + 行距 ≤ 5 行**被两个引擎独立命中。
实测本项目样本里语义审查的产出全部落在规则覆盖不到的位置（语义 13 条，0 条与静态重合），
恰恰说明语义引擎补的是盲区而不是重复劳动。页面上把这一项显示为 0 并附悬停说明，
不做任何"凑数"处理。

## 10. 故障速查

| 现象 | 原因 | 处理 |
|---|---|---|
| 启动报 `Web server failed to start. Port 55853 was already in use`（端口不是 8080） | 宿主环境（IDE / 桌面工具 / 沙箱）为子进程注入了 `SERVER_PORT`。**Spring 里环境变量优先级高于 application.yml**，即使配置写的是 `${APP_SERVER_PORT:8080}` 也会被 `SERVER_PORT` 覆盖 | 启动时显式加 `--server.port=8080`（命令行参数优先级最高）：`mvn spring-boot:run "-Dspring-boot.run.arguments=--server.port=8080"`；IDEA 里在 Program arguments 填 `--server.port=8080` |
| `java -version` **没有任何输出**、退出码却是 0 | PATH 里第一个 java 是 `C:\Program Files\Common Files\Oracle\Java\javapath\java.exe` 空壳（本机实测就是这种情况，正常版本在 `D:\jdk-21`） | 把 JDK 21 的 `bin` 目录前移到 PATH 最前，或统一依赖 `JAVA_HOME`。自检脚本已优先读 `JAVA_HOME`，不会再被空壳骗 |
| `Bind for 0.0.0.0:5432 failed: port is already allocated` | 本机已装 PostgreSQL | `deploy\.env` 改 `DB_PORT=15432`，**同时**给后端设环境变量 `DB_PORT=15432` |
| `Extension "vector" is not available` | 用错镜像 | 必须 `pgvector/pgvector:pg16`，官方 `postgres` 不含 pgvector |
| 后端启动 `Connection refused` | 容器没起或没 healthy | `docker compose ps` 看状态，`logs postgres` 看原因 |
| 登录返回 503 | Redis 不可用，令牌黑名单 fail-closed | 起 redis；检查 `REDIS_PASSWORD` 是否被设成了非空 |
| 登录 401 但密码没错 | 连错 5 次被锁 15 分钟 | 等锁过期，或 `docker exec cr-redis redis-cli del auth:loginlock:admin` |
| `docker compose` 报找不到文件 | 在错误目录执行 | 一律用本文的 `--env-file` + `-f` 全路径写法，与当前目录无关 |
| 前端 401 死循环 | 后端未起，或改了 `APP_JWT_SECRET` 但沿用旧 Cookie | 清站点 Cookie 重登；看 Network 里 `/api/auth/refresh` 的返回 |
| `mvn` 找不到或报版本错 | 只装了 JRE / PATH 未配 | 装 JDK 21，`java -version` 必须显示 `21.x` |
| `npm run dev` 端口占用 | 5173 被占（`strictPort: true`，不会自动换端口） | 关掉占用的进程，或临时改 `vite.config.ts` 的 `server.port` 并同步改 `APP_CORS_ORIGINS` |

## 11. 附：五个容器分别干什么、什么时候需要

| 容器 | 镜像 | 作用 | 何时需要 |
|---|---|---|---|
| `postgres` | `pgvector/pgvector:pg16` | 业务库 + 向量库（同一实例，`vector(1024)` 列） | 始终 |
| `redis` | `redis:7.4-alpine` | 刷新令牌、令牌黑名单、登录失败计数、后续任务队列 | 始终 |
| `minio` | `minio/minio` | 代码包 zip、知识库原始文档 | M6 起 |
| `embedding` | `text-embeddings-inference:cpu-1.8` | BGE-M3 向量化（1024 维，L2 归一化） | M3 起 |
| `embedding-fastapi` | 自建 `embedding/Dockerfile` | 同上，备选实现（`--profile fastapi`） | 排障对比用 |

> Redis 的 `maxmemory-policy` 固定为 `noeviction`，不要改成 `allkeys-lru`：
> 那会把刷新令牌和黑名单当缓存驱逐掉，表现为用户莫名掉线、已登出的令牌重新可用。

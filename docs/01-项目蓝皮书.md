## 1. 项目定位

一句话：**用"静态分析 + 大模型语义分析"双引擎替代人工代码审查的第一道筛查，输出带定位、带修复建议、可追溯的审查报告。**

与传统方案的本质差别不在"能不能查"，而在三个机制的配合：

| 对比对象 | 它的做法 | 本系统的差别 |
|---|---|---|
| PMD / SpotBugs / SonarQube | 规则匹配，源码/字节码级 | 补上语义层判断，减少"看不懂业务逻辑"的漏报 |
| 直接调 ChatGPT 审代码 | 一次性 Prompt，输出自由文本 | 结构化输出约束 + 历史缺陷库 RAG + 静态结果交叉验证，压住幻觉 |
| 现有 AI 审查插件 | 全量扫描，逐文件送模型 | 增量审查：只审 Git diff 命中的方法，成本可控 |

答辩时"你的创新点"就答这三层，每层都有可演示的证据。

## 2. 目标与范围

### 2.1 必须做到（P0，不做完不能答辩）

1. 三角色登录与 RBAC 权限隔离
2. 代码仓库接入（Git URL / 代码包上传两种方式）
3. 审查任务创建、异步执行、进度实时可见
4. 静态分析引擎可独立跑通并输出结构化缺陷
5. 语义分析引擎可独立跑通并输出结构化缺陷 + 修复建议
6. 双引擎结果融合，输出统一审查报告
7. 审查报告前端呈现：问题列表、代码定位、建议对照
8. 问题闭环：确认 / 误报 / 已修复 状态流转
9. 对比实验数据（三方案 × 三指标）

### 2.2 争取做到（P1）

10. RAG 历史缺陷库检索增强
11. 增量审查（Git diff 定位 → 方法级切片）
12. 质量看板（缺陷趋势、类型分布、开发者维度）
13. 审查意见模板库
14. 审计日志

### 2.3 深度增强模块（v1.3：六项全做，共 14 天）

P0 九项能保证"做得完"，但**做完了不够"看得见"**。下面六个模块不是加功能数量，而是加"可验证的深度"，每个都能在答辩现场跑一次给评委看。详细设计见 6.7。

| # | 模块 | 解决什么质疑 | 答辩可见性 | 工作量 | 建议 |
|---|---|---|---|---|---|
| E1 | 三方案对比沙盘 | "你和直接调 API 有啥区别" | ★★★★★ 一屏三列对比 | 2 天 | **必做** |
| E2 | 缺陷回流双库（正/负样本） | "RAG 是不是摆设" | ★★★★★ 误报率下降曲线 | 3 天 | **必做** |
| E3 | 修复建议可验证（语法/编译） | "AI 建议能信吗" | ★★★★ 徽标 + 编译日志 | 2 天 | **必做** |
| E4 | 跨文件上下文（1 跳调用链） | "凭什么叫语义审查" | ★★★ 对比实验多一组 | 3 天 | **必做（v1.3 确认）** |
| E5 | 审查策略引擎 | "规则写死了怎么适配团队" | ★★★ 配置即生效 | 2 天 | **必做（v1.3 确认）** |
| E6 | 置信度校准（人工反馈驱动） | "置信度是拍脑袋定的吗" | ★★★ 校准表 | 2 天 | **必做（v1.3 确认）** |

**取舍原则**：六项全做，合计 **14 天**（已确认，见第 16 章）。这个投入是值的——六项合起来覆盖第 17 章 Q1–Q4 四个高危追问（E1 挡"只是叠表"、E2 挡"RAG 是摆设"、E3 挡"建议不可信"、E6 挡"置信度拍脑袋"），缺哪项就在那个问题上失守；E4/E5 则分别支撑"语义深度"与"团队适配"两条追问。

**若进度落后，按 E4 → E5 → E6 的顺序降级**（保留 E1/E2/E3 不动）：
1. 先砍 **E4**（3 天，最重，且只是加深语义召回）→ 总 11 天
2. 再砍 **E5** → 总 9 天
3. **E6 最后砍**——它直接支撑 Q4「置信度怎么定的」这个四星问题，且实现最轻（一次聚合任务 + 一张统计表）

> 红线：E1/E2/E3 无论如何不砍。它们决定"评委觉得简不简单"，砍了就回到 v1.0 的评价水平。

### 2.4 边界决策：四项"看起来该做"的功能怎么处理

审批流、通知中心、多编程语言、移动端，这四项是毕设评审时最常被问"你怎么没做"的功能。结论不是简单砍掉，而是**每一项都换成成本更低、收益更高的做法**——这张表既是开发约束，也是答辩时的标准答案。

| 功能 | 决策 | 替代方案 | 增量成本 | 为什么不做（答辩用） |
|---|---|---|---|---|
| **审批流** | 不做流程引擎（不引 Flowable/Activiti） | **合并门禁（Merge Gate）**：审查结论直接决定能否放行，规则可配（见 6.8） | +1.5 天 | 真实研发流程（GitHub PR / GitLab MR）不存在多级审批，靠的是"必须 approve 才能 merge"的轻量门禁；做重审批流反而**脱离业务**，且技术上只是状态机 + 待办列表 |
| **通知中心** | 不做独立页面、不做多渠道、不做订阅配置 | 保留**事件推送薄层**：仅"审查完成""问题指派给我"两类事件，复用已有 SSE 通道（第 3 章功能 7） | 0 | 消息分类/已读未读/邮件短信通道会持续膨胀；同样一套 SSE，叫"通知中心"是管理功能，叫"审查进度实时推送"才是技术点 |
| **多编程语言** | 只支持 **Java**，Python/JS/Go 列入展望 | **引擎插件化**：抽象 `StaticAnalyzer` SPI，Java 是唯一实现（见 6.2.1） | +0.5 天 | PMD 只支持 Java，JS/Python/Go 需分别接 ESLint/Pylint/golangci-lint，等于 N 套工具 + N 套 AST 适配 + N 套 Prompt + N 套测试集，工作量是**乘法不是加法**，结果每个语言都只能跑 demo |
| **移动端** | 不做 App / 小程序 / H5 独立端 | **响应式布局**（报告页手机浏览器可看）+ 可选**企业微信/钉钉机器人推送**（webhook 约半天） | +0.5 天 | 代码审查本质是"看代码 diff"的场景，小屏无法有效 review，属伪需求；两套技术栈割裂，且被问"为什么做移动端"只能答"为了演示方便" |

**三条判断依据**（答辩时可直接讲）：

1. **都不影响核心指标**。这四项没有一项影响"缺陷发现得准不准、AI 结论可不可信"，全在外围。外围功能做得再多也不加深，只会稀释核心模块的时间。
2. **本科毕设的评分逻辑是深度 > 广度**。评委反感"什么都做了但什么都浅"，认可"知道边界在哪"。可讲金句：*"我宁可把一个引擎做到可验证，也不愿接五个引擎都只能演示 hello world。"*
3. **风险不对称**。加功能的收益是"或许加分"，成本是"挤占核心模块时间 + 每项都做浅 → 被追问细节答不上"。收益不确定、成本确定，所以必须砍。

四项替代方案合计仅 **+2.5 天**，换来的是"边界清晰、每项都有讲头"——比盲目加功能划算得多。

其余明确不做（写进论文"展望"）：

- 不做多人实时协同评审（仅单人复核）
- 不做 CI/CD 平台对接（不接 Jenkins/GitLab CI，仅 Webhook 预留）
- 不做代码自动提交修复（只给建议，不代改代码）
- 不做模型微调（只做 Prompt 工程 + RAG）

> 范围收敛是毕设能否做完的关键。上面"不做"的每一条都要在论文里写成"后续工作"，反而显得有边界感。

| 代码解析 | JavaParser 3.26 | 方法级切片，PMD 之外自带轻量定位能力 |
| Git 操作 | JGit 6.9 | 拉取仓库、解析 diff |
| LLM 接入 | **DeepSeek**（Spring AI 1.0，OpenAI 兼容协议） | 已确认选型。Key 走**系统环境变量 `DEEPSEEK_API_KEY`**，由 `application.yml` 的 `${DEEPSEEK_API_KEY}` 占位符注入，**不入库、不写进配置、不进 git** |

### 4.3 部署

Docker Compose 单机编排 6 个服务：`postgres`、`redis`、`minio`、**`embedding`（BGE-M3）**、`backend`、`frontend(nginx)`。开发期用 `docker-compose.dev.yml` 只起中间件 + embedding，前后端本地跑，热更新快。

**环境变量约定**（`.env` 与 `.env.example` 分离，`.env` 进 `.gitignore`）：

| 变量 | 来源 | 说明 |
|---|---|---|
| `DEEPSEEK_API_KEY` | **系统环境变量**，Compose 用 `environment: - DEEPSEEK_API_KEY` 透传 | 不落盘、不进 git；`application.yml` 用 `${DEEPSEEK_API_KEY:}` 占位，缺失时启动告警但不崩 |
| `DEEPSEEK_BASE_URL` | 默认 `https://api.deepseek.com` | OpenAI 兼容端点 |
| `EMBEDDING_BASE_URL` | 默认 `http://embedding:8080` | 本地 BGE-M3 服务 |
| `DB_*` / `REDIS_*` / `MINIO_*` | `.env` | 中间件连接信息 |

**BGE-M3 服务的两种落地方式**（M0 阶段二选一，都约 0.5 天）：

| 方式 | 镜像/依赖 | 优点 | 缺点 |
|---|---|---|---|
| **TEI**（推荐） | `ghcr.io/huggingface/text-embeddings-inference:cpu-1.5` + `--model-id BAAI/bge-m3` | 零代码，自带 `/embed` 批量接口与批处理优化 | 镜像较大（~1.5GB），首次拉模型需联网 |
| FastAPI 自写 | `python:3.11` + `sentence-transformers` | 完全可控，可加自定义归一化 | 要自己写批处理与健康检查 |

CPU 推理单条约 50–200ms，知识库批量构建 500 条片段约 1–2 分钟，答辩演示完全够用；有 GPU 时改 `--device cuda` 即可。

## 5. 系统架构

### 5.1 分层

```
┌──────────────────────────────────────────────────────────┐
│  前端 SPA (Vue3)                                          │
│  登录 / 工作台 / 项目 / 任务 / 报告 / 看板 / 配置          │
└───────────────────────┬──────────────────────────────────┘
                        │ HTTPS + JWT
┌───────────────────────▼──────────────────────────────────┐
│  接入层  Controller（参数校验、权限注解、统一响应）        │
├──────────────────────────────────────────────────────────┤
│  应用层  Service（事务边界、编排）                         │
│    AuthService / ProjectService / TaskService             │
│    ReportService / StatsService / ConfigService           │
├──────────────────────────────────────────────────────────┤
│  领域层  Engine（核心，可独立单测）                        │
│    StaticAnalyzer(PMD/SpotBugs)  SemanticAnalyzer(LLM)    │
│    DefectFuser   IncrementalSlicer   RagRetriever         │
├──────────────────────────────────────────────────────────┤
│  基础设施层                                                │
│    Mapper / Redis / MinIO / JGit / LLM / Embedder         │
└──────────────────────────────────────────────────────────┘
```

**分层纪律**：`Engine` 层不允许出现 `HttpServletRequest`、不允许直接读写数据库。引擎只接收"代码文本 + 配置"，返回"缺陷列表"。这样对比实验可以脱离 Web 层直接跑，写论文时用来批量出数据。

### 5.2 审查主流程时序

```
开发者            TaskService        Redis队列      Worker           引擎组
  │  POST /tasks     │                  │            │                │
  ├─────────────────>│ 校验+落库(CREATED)│            │                │
  │                  ├──push taskId────>│            │                │
  │<── 202 taskId ───┤                  │            │                │
  │                  │                  ├──poll─────>│                │
  │                  │                  │            ├─1 拉取代码─────>│
  │                  │                  │            ├─2 增量切片──────┤
  │                  │                  │            ├─3 静态分析──────┤
  │                  │                  │            ├─4 RAG召回───────┤
  │                  │                  │            ├─5 语义审查──────┤
  │                  │                  │            ├─6 融合──────────┤
  │                  │                  │            ├─7 落库+统计─────┤
  │  SSE /sse/task   │<─────────────────┼────────────┤ 进度推送         │
  │<── 实时进度 ─────┤                  │            │                │
```

**状态机**：`CREATED → QUEUED → FETCHING → SLICING → ANALYZING → FUSING → DONE`，任一步失败进 `FAILED` 并记录 `fail_stage`。前端进度条按状态映射，失败要能显示"卡在哪一步"，这是答辩演示的加分点。

## 6. 核心机制设计

### 6.1 统一缺陷模型（整个系统的地基）

静态结果和 LLM 结果必须归一到同一结构，否则无法融合。

```
Defect {
  filePath      String      相对路径
  startLine     int
  endLine       int
  category      Enum        NULL_POINTER / RESOURCE_LEAK / CONCURRENCY /
                            INJECTION / PERFORMANCE / MAINTAINABILITY /
                            LOGIC_ERROR / CODE_STYLE
  severity      Enum        BLOCKER / CRITICAL / MAJOR / MINOR / INFO
  title         String      一句话结论
  description   String      详细说明
  suggestion    String      修复建议（LLM 专属，静态可为空）
  fixSnippet    String      修复代码片段（可空）
  source        Enum        STATIC / LLM / FUSED
  ruleId        String      PMD 规则名 或 prompt 模板 id
  confidence    double      0~1
  evidence      List<String> 各引擎原始证据（供人工复核）
}
```

**类别映射表**是融合的前提：PMD 的 `NullPointerException`→`NULL_POINTER`、`CloseResource`→`RESOURCE_LEAK`、`AvoidDuplicateLiterals`→`CODE_STYLE`……建一张约 40 条的映射配置表（`rule_category_map`），答辩被问"你怎么对齐两套体系"时直接展示这张表。

### 6.2 静态分析引擎

| 引擎 | 分析对象 | 是否需编译 | 定位 |
|---|---|---|---|
| **PMD 7** | Java 源码 AST | 否 | **主引擎，必选** |
| SpotBugs 4.8 | 编译后的 .class | **是** | 可选增强 |

**为什么 PMD 做主引擎**：SpotBugs 分析字节码，被审查项目必须先 `mvn compile` 成功才能用。真实项目大量编译不过（缺依赖、私有包、JDK 版本不符），演示极容易卡在"编译失败"。因此：

```
静态引擎策略：
  1. 始终跑 PMD（源码级，零依赖，稳定）
  2. 任务配置开启 SpotBugs 且项目可编译时，附加跑 SpotBugs
  3. 编译失败不阻断任务，记录 warning，降级为 PMD-only
```

这个降级设计要写进论文第 4 章"双引擎审查机制设计"，是很实在的工程考量。

实现要点：
- PMD 以 Java API 内嵌调用（非命令行），避免进程开销与超时失控
- 规则集可通过 `rule_config` 表动态开关，改配置不重启
- 超时：单文件 3s，整任务 5min，超时截断并标记 `PARTIAL`

#### 6.2.1 引擎插件化接口（多语言扩展性的交代）

只做 Java ≠ 架构封闭。把静态分析抽象成 SPI，既回答了"为什么只支持 Java"，又不用真去写多语言实现：

```java
public interface StaticAnalyzer {
    String name();                                  // "pmd" / "spotbugs" / 未来的 "eslint"
    Set<String> supportedLanguages();               // {"java"} / {"javascript"}
    boolean requiresCompile();                      // PMD=false, SpotBugs=true
    int priority();                                 // 执行顺序，PMD 先跑
    List<RawDefect> analyze(AnalysisContext ctx);   // 输入：源码/字节码 + 规则集
}
```

- 实现类用 `@Component` 自动注册，`AnalyzerRegistry` 按 `supportedLanguages` 与 `engine_flags` 过滤调度——**新增语言 = 新增一个实现类，不改任务编排代码**
- `RawDefect` 是统一缺陷模型的原始形态（见 6.1），各引擎只负责"翻译成这个结构"，融合层不感知具体引擎
- 论文第 4 章写一句即可："引擎层采用 SPI 插件化设计，当前实现 Java 分析器，扩展新语言无需修改调度层"
- **答辩话术**（对应第 17 章 Q7）："Java 生态的静态分析工具最成熟（PMD、SpotBugs 都有稳定的 Java API），能把双引擎融合做深；架构上引擎是插拔的，接 ESLint 只需实现一个接口。但我选择先把一个语言做到可验证，而不是铺开五个语言都只能跑 demo。"

### 6.3 语义分析引擎（LLM）

**输入不是整个文件，而是"切片"**（见 6.4），每个切片独立一次调用，便于并行与定位。

Prompt 结构（三段式，存 `prompt_template` 表可在线改）：

```
[系统角色] 你是一名资深 Java 代码评审专家，只输出 JSON。
[审查规则] <注入：团队规范摘要 + 历史相似缺陷 few-shot（RAG）>
[待审代码] <带行号的方法体>
[输出格式] {"defects":[{"startLine":..,"category":"..","severity":"..",
           "title":"..","description":"..","suggestion":"..","fixSnippet":".."}]}
```

**压幻觉的三道约束**（答辩必问）：
1. **结构化输出**：强制 JSON Schema，解析失败重试 1 次，再失败该切片标记 `SEMANTIC_SKIPPED` 而不抛错
2. **行号约束**：Prompt 里代码带行号且要求"startLine 必须落在给定区间内"，越界结果直接丢弃（这一条能砍掉大部分幻觉）
3. **RAG 兜底**：见 6.5，只靠模型自由发挥的问题降级为"建议"级别

**成本控制**：切片级并行（线程池 4~8）、结果按 `methodHash` 缓存、单任务 token 上限截断，配置项 `engine.llm.max-tokens-per-task`。

### 6.4 增量审查与代码切片

```
1. JGit 拉取 base..head 的 diff
2. 解析 unified diff → 变更行区间集合 {filePath: [(newStart,newEnd)]}
3. JavaParser 解析变更文件 → 方法/类信息（含行号范围）
4. 与变更行求交：命中方法即为"待审单元"，未命中但受影响（被调用）的标记为上下文
5. 未变更文件直接跳过
6. 缓存 key = sha256(filePath + methodBody + promptVersion)，命中则复用上次结果
```

**全量 vs 增量**两种模式都要保留：全量用于首次接入仓库（基线），增量用于日常提交。对比实验里"耗时"指标就靠这个拉开差距。

### 6.5 RAG 设计

| 环节 | 做法 |
|---|---|
| 语料来源 ① | 已确认缺陷（`issue.status = CONFIRMED/FIXED`）代码片段 + 诊断 + 修复 |
| 语料来源 ② | 团队编码规范文档（PDF/DOCX/MD 上传） |
| 切分 | 缺陷条目整体成 chunk；文档按 500 token + 50 overlap |
| 向量化 | **BGE-M3 本地服务**（已确认，1024 维，服务端 L2 归一化后存 pgvector）；阿里 `text-embedding-v3` 仅作断网/故障备选，同为 1024 维可直接切换 |
| 索引 | HNSW（`m=16, ef_construction=64`），cosine 距离 |
| 检索 | top-k=5，相似度阈值 0.75，低于阈值视为"无参考" |
| 注入 | 检索结果作为 few-shot 样例拼进 Prompt，同时写入 `issue.evidence` 供溯源 |

**溯源是关键设计**：报告里每条 LLM 缺陷都能点开"依据哪条历史缺陷/哪段规范"，这是本系统区别于"裸调 API"的可验证证据。

### 6.6 融合算法（论文核心章节）

三步走：**归并 → 加权 → 裁决**。

**① 位置归并**

同文件下，满足以下任一即视为同一缺陷簇：
- 行区间有交集，且 `category` 相同
- 区间中心距 ≤ 3 行，且 `category` 相同

**② 置信度加权**

```
conf_static = rule_weight               (可配，默认 0.80)
conf_llm    = model_confidence * 0.7 + rag_bonus
              rag_bonus: 命中历史缺陷 +0.2，命中规范 +0.1，上限 1.0
```

**③ 融合规则表**

| 情形 | 处理 | severity | confidence | 标记 |
|---|---|---|---|---|
| 双引擎均命中 | 合并，保留更详细的建议 | **提升一级** | `1-(1-c1)(1-c2)` | CROSS_VALIDATED |
| 仅静态命中 | 保留 | 不变 | `c*0.9` | STATIC_ONLY |
| 仅 LLM 命中 + RAG 命中 | 保留 | 不变 | 原值 | LLM_RAG |
| 仅 LLM 命中 + RAG 未命中 | **降为 INFO 或进人工队列** | 降一级 | `c*0.6` | LLM_ONLY |
| 同位置结论冲突 | 不自动裁决，进复核队列 | 取高 | — | CONFLICT |

`CROSS_VALIDATED` 的问题在报告里用特殊标记展示——"两个引擎都指向这里"，这是最有说服力的缺陷。

### 6.7 深度增强模块设计（v1.1 新增）

> 六个模块的共同特征：**不新增"管理功能"，只加深"已有能力的可验证性"**。每一条都能对应论文里的一句话结论。

#### 6.7.1 E1 · 三方案对比沙盘（Analog Lab）

**目的**：把第 13.3 节的对比实验从"论文里的一张表"变成"现场可跑的一屏"。评委最想看的就是"你这套融合到底比单干强在哪"。

**设计**

```
POST /api/lab/compare
body: { sourceType: "COMMIT" | "SNIPPET",
        projectId, baseCommit, headCommit,   // COMMIT 模式
        code, fileName,                       // SNIPPET 模式
        flags: { pmd:true, llm:true, rag:true } }

后端并行跑三条链路（复用现有引擎，不写新分析逻辑）：
  A 路 = PmdAnalyzer                → defectsA
  B 路 = LlmAnalyzer(无静态结果)     → defectsB
  C 路 = Fuser(A ∪ B)               → defectsC
差异集：
  onlyStatic = A - C    （被融合降级/合并的静态误报）
  onlyLlm    = B - C    （被 RAG 负样本或行号约束过滤的幻觉）
  onlyFused  = C - A - B（不，恒为空；改为：crossValidated = A ∩ B）
  downgraded = 严重度被下调的条目
返回三分结果 + 差异集 + 各自耗时/token
```

**前端**：三列并排（仅静态 / 仅大模型 / 双引擎融合），差异用色块标注：绿色=仅融合发现、黄色=被降级、灰色=被过滤。底部一行"融合相对单一方案：多发现 X 条、过滤 Y 条"。

**答辩话术**："这一屏不是我挑出来的例子，是任意 commit 都能跑的结果。"

#### 6.7.2 E2 · 缺陷回流双库（Positive / Negative KB）

**目的**：把 RAG 从"我建了个向量库"升级为"系统越用越准"，并且这个"变准"是**可度量、可画曲线**的。

**设计**

`defect_kb` 改造（加三列）：

```sql
ALTER TABLE defect_kb
  ADD COLUMN polarity   VARCHAR(8)  NOT NULL DEFAULT 'POSITIVE', -- POSITIVE / NEGATIVE
  ADD COLUMN hit_count  INT         NOT NULL DEFAULT 0,
  ADD COLUMN last_hit_at TIMESTAMPTZ;
CREATE INDEX idx_defect_kb_polarity ON defect_kb(polarity);
```

**回流触发点**

| 人工动作 | 回流动作 |
|---|---|
| 问题被裁决为 CONFIRMED / FIXED | 写入 POSITIVE（代码片段 + 诊断 + 修复） |
| 问题被裁决为 FALSE_POSITIVE | 写入 NEGATIVE（代码片段 + "此处不是缺陷，原因是…"） |
| 审查者补充人工意见 | 若有实质结论，作为 POSITIVE 的补充说明 |

**检索时的双段注入**（这是关键）

```
【已知同类缺陷（请参考其判定口径）】  ← POSITIVE top-k
【已判定为误报，请勿再报】            ← NEGATIVE top-k
```

**硬性过滤**：LLM-only 的缺陷若与某条 NEGATIVE 相似度 > 0.85，直接丢弃并记 `flag = FILTERED_BY_NEG`。这一步比"调低 temperature"管用得多。

**度量**：`GET /api/stats/kb-growth` 返回按周的正/负样本累计量与同期误报率，前端画双轴曲线。答辩时这条"误报率随样本积累下降"的曲线，比任何形容词都有说服力。

#### 6.7.3 E3 · 修复建议可验证（语法 + 编译双级）

**目的**：让"AI 给出的修复建议"从"看着像代码"变成"能过解析/能过编译"，这是硬指标。

**设计**

```
L1 语法校验（永远执行，成本极低）
  用 JavaParser 解析 fixSnippet；若片段是语句级，包装进空方法体再解析
  → 通过：fix_verified = SYNTAX_OK
  → 失败：SYNTAX_FAIL，并把 LLM 建议降为 INFO 级

L2 编译校验（项目可编译且任务开启时异步执行）
  临时工作区 git apply patch → mvn -q -o compile（限时 120s）
  → BUILD SUCCESS：COMPILE_OK
  → BUILD FAILURE：COMPILE_FAIL，附编译错误首行
```

`review_issue` 增加 `fix_verified VARCHAR(16)`。

**前端**：建议卡片右上角一个徽标（✓ 语法通过 / ✓✓ 编译通过 / ⚠ 建议需人工确认），点开看编译日志。

**答辩话术**："我的系统不会给你一段编不过的代码——语法校验是必过的，能编译的项目还会跑一次 compile。"

#### 6.7.4 E4 · 跨文件上下文（1 跳调用链）

**目的**：解决"只贴一个方法，模型看不到调用方传了什么参数"的先天缺陷。这是"语义审查"名副其实的前提。

**设计**

```
1. JavaParser 解析项目 → 建轻量索引：类 → 方法 → 签名 + 行号范围
2. 对变更方法 M：
     caller  = 直接调用 M 的方法（最多 2 个，取实现片段前 40 行）
     callee  = M 内调用的项目内方法的签名（只签名，不取实现）
3. 拼成【相关上下文】块注入 Prompt，受 token 预算约束（默认 ≤ 1500 token）
4. 索引缓存到 Redis（key = projectId + commit），避免重复解析
```

**度量**：对比实验增加第四组"语义引擎（无上下文）vs 语义引擎（有上下文）"，用同一批样本跑，这本身就是论文里一个可写的小实验。

#### 6.7.5 E5 · 审查策略引擎（项目画像 → 策略）

**目的**：把"规则开关"升级为"按代码重要度差异化审查"。核心模块的 P0 问题不该和 /utils 里的命名风格同级。

**设计**

```sql
CREATE TABLE review_strategy (
  id BIGSERIAL PRIMARY KEY,
  name VARCHAR(64) NOT NULL,
  scope VARCHAR(16) NOT NULL,           -- GLOBAL / PROJECT
  project_id BIGINT,
  match_expr VARCHAR(256),              -- 如 src/main/java/**/core/**
  severity_offset INT DEFAULT 0,        -- 命中后严重度整体 ±N 级
  confidence_weight NUMERIC(3,2) DEFAULT 1.00,
  llm_budget_tokens INT,                -- 该范围的可调预算
  engine_flags JSONB,                   -- 覆盖默认引擎开关
  priority INT DEFAULT 100,             -- 多条命中时按优先级合并
  enabled BOOLEAN DEFAULT TRUE
);
```

**合并规则**：按 `priority` 从高到低逐条应用，`severity_offset` 累加后裁剪到 [BLOCKER, INFO]；`confidence_weight` 相乘。

**前端**：策略表格 + 一个"命中预览"输入框（贴路径看命中哪几条），配置改完立即对新任务生效。

#### 6.7.6 E6 · 置信度校准（人工反馈驱动）

**目的**：回应"你的 confidence 0.8 是怎么来的"。答案不是"我定的"，而是"由历史裁决结果统计出来的"。

**设计**

```
真值来源：人工裁决（CONFIRMED / FALSE_POSITIVE）
统计维度：flag（CROSS_VALIDATED / STATIC_ONLY / LLM_RAG / LLM_ONLY）× category
准确率：acc = (TP + 1) / (TP + FP + 2)        ← 拉普拉斯平滑，避免小样本极端值
校准后置信度：conf' = conf * acc(flag, category) ^ λ,  λ 默认 0.5（可配）
最小样本量：样本 < 10 时不做校准，沿用原始值（避免早期失真）
```

**物化**：定时任务每日聚合到 `flag_accuracy` 表，页面 `GET /api/stats/calibration` 直接读表，避免实时算。

```sql
CREATE TABLE flag_accuracy (
  id BIGSERIAL PRIMARY KEY,
  flag VARCHAR(24) NOT NULL,
  category VARCHAR(32) NOT NULL,
  sample_cnt INT NOT NULL,
  tp INT NOT NULL,
  fp INT NOT NULL,
  accuracy NUMERIC(4,3),
  calibrated_at TIMESTAMPTZ DEFAULT now(),
  UNIQUE (flag, category)
);
```

**前端**：校准表（flag / 样本数 / 准确率 / 当前权重）+ 一条说明"样本 < 10 不校准"。

#### 6.7.7 六个模块的落地顺序

```
Day 1-2   E3（最简单，先拿一个"可验证"的成果）
Day 3-5   E2（涉及裁决回流与检索双段注入，改动面最大）
Day 6-7   E1（纯展示层，复用已有引擎，见效最快放在中期做也行）
Day 8-10  E4（调用链索引）
```

### 6.8 合并门禁（Merge Gate）—— 替代审批流

**为什么不做审批流**：GitHub PR / GitLab MR 的通行做法是"必须有人 approve 才能 merge"的**轻量门禁**，真实研发流程里不存在多级审批。引 Flowable 做流程引擎既脱离业务场景，技术上也只是状态机 + 待办列表，答辩讲不出深度（见 2.4 决策表）。

**门禁的本质**：把"审查结论"升级为"能否合入"的**判定**。这一步让系统从"一个出报告的工具"变成"研发流程里的质量卡点"——也是它能被真实团队用起来的唯一理由。

#### 6.8.1 判定模型（三态）

判定 = 策略规则 + 缺陷直方图 + 豁免过滤，输出三态（严重度沿用 6.1 五级枚举，下表用中文简称：致命=`BLOCKER`、严重=`CRITICAL`、一般=`MAJOR`）：

| 结论 | 触发条件（默认策略） | 前端表现 |
|---|---|---|
| `PASS` 通过 | 致命 = 0 且 严重 = 0 且 一般 ≤ 阈值 | 绿色徽标 + 可复制的 commit 注释 |
| `WARN` 警告 | 致命 = 0 且 严重 = 0，但一般问题超阈值 | 黄色徽标 + "建议修复后再合入" |
| `BLOCK` 拦截 | 致命 > 0 或 严重 > 0（且未被豁免） | 红色徽标 + 阻断项清单（可点进代码行） |

**核心约束：只拦"确定性问题"。** 默认仅 `BLOCKER`/`CRITICAL` 级别阻断，且必须同时满足"非误报"（`status != FALSE_POSITIVE`）与"未豁免"。这样门禁不会因为大模型的一条可疑建议就把人卡死——这是它能真实可用的前提，也是答辩时最容易被追问的点。

#### 6.8.2 策略表

```sql
CREATE TABLE review_gate_policy (
  id                BIGSERIAL PRIMARY KEY,
  project_id        BIGINT REFERENCES repo_project(id),      -- NULL = 全局默认
  name              VARCHAR(64)  NOT NULL,
  enabled           BOOLEAN      NOT NULL DEFAULT TRUE,
  block_severity    VARCHAR(16)  NOT NULL DEFAULT 'CRITICAL', -- 阻断起始级别
  max_general       INT          NOT NULL DEFAULT 20,         -- 一般问题上限
  ignore_paths      TEXT[],                                   -- 豁免路径，如 {'**/test/**'}
  ignore_categories TEXT[],                                   -- 豁免类别，如 {'STYLE'}
  owner_bypass      BOOLEAN      NOT NULL DEFAULT TRUE,       -- 管理员可强制放行
  created_at        TIMESTAMP    NOT NULL DEFAULT now()
);
```

#### 6.8.3 判定流程与接口

```
任务 DONE → 统计各严重度数量 → 按路径/类别过滤豁免项
   ├─ 存在未豁免的 BLOCKER/CRITICAL → BLOCK
   ├─ 一般问题数 > max_general     → WARN
   └─ 否则                          → PASS
```

- `GET /api/tasks/{id}/gate`：取当前判定与阻断项清单（报告页顶部徽标）
- `POST /api/tasks/{id}/gate/override`：管理员强制放行，**强制写审计日志并记录理由**
- 判定结果落入 `review_task.gate_result` + `gate_json`（阻断项快照），保证历史可回溯
- 门禁判定在任务状态机的 `DONE` 之后触发，**判定失败不影响任务本身状态**（门禁是附加结论，不是任务环节）

#### 6.8.4 答辩话术

> "我的系统不只出一份报告，它把审查结论变成了**合并的前置条件**：存在未豁免的致命/严重缺陷时，门禁直接拦截；管理员可以强制放行，但必须填理由并留审计痕迹。这样它就从'一个扫描工具'变成了'研发流程里的质量卡点'——这也是它能被真实团队用起来的原因。"

这段话同时解决第 17 章 Q10（能落地吗）与"和 SonarQube 有什么区别"两个问题。

```sql
  id            BIGSERIAL PRIMARY KEY,
  task_id       BIGINT NOT NULL REFERENCES review_task(id) ON DELETE CASCADE,
  project_id    BIGINT NOT NULL,
  file_path     VARCHAR(512) NOT NULL,
  start_line    INT NOT NULL,
  end_line      INT NOT NULL,

  severity      VARCHAR(16) NOT NULL,

  description   TEXT,
  suggestion    TEXT,
  fix_snippet   TEXT,
  source        VARCHAR(16) NOT NULL,       -- STATIC / LLM / FUSED
  rule_id       VARCHAR(128),
  confidence    NUMERIC(4,3),
  flag          VARCHAR(24),                -- CROSS_VALIDATED / STATIC_ONLY / LLM_ONLY / LLM_RAG / CONFLICT
  status        VARCHAR(24) DEFAULT 'OPEN', -- OPEN / CONFIRMED / FALSE_POSITIVE / FIXED / WONTFIX
  evidence      JSONB,                      -- 各引擎原始输出 + RAG 命中
  assigned_to   BIGINT,
  created_at    TIMESTAMPTZ DEFAULT now()
);
CREATE INDEX idx_issue_task ON review_issue(task_id);
CREATE INDEX idx_issue_status ON review_issue(project_id, status);

CREATE TABLE defect_kb (
  id          BIGSERIAL PRIMARY KEY,
  category    VARCHAR(32),
  code_snippet TEXT NOT NULL,
  diagnosis   TEXT NOT NULL,
  fix_summary TEXT,
  source_issue_id BIGINT,
  embedding   vector(1024),
  created_at  TIMESTAMPTZ DEFAULT now()
);
CREATE INDEX idx_defect_kb_vec ON defect_kb
  USING hnsw (embedding vector_cosine_ops) WITH (m=16, ef_construction=64);
```

**设计要点**：`evidence` 用 JSONB 存两路原始证据，融合算法和人工复核都靠它；`stats_json` 存耗时与 token，性能实验数据直接从库里出，不用手工记。

**两个主舞台**：
1. **审查报告页**——点问题→代码自动滚到行→右侧显示"静态引擎怎么说 / 大模型怎么说 / 建议怎么改"，一个页面把融合机制讲完。
2. **对比沙盘页**——同一份代码三列并排，绿色标"只有融合才发现"、灰色标"被过滤的幻觉"，评委自己看差异，不用你解释。

**关于移动端**（见 2.4 决策）：不做 App / 小程序 / 独立 H5，只做**响应式**——审查报告页与门禁徽标在窄屏下切为单列（问题列表在上、代码在下），保证答辩时用手机打开链接也能看。实现方式：Element Plus 栅格 + 少量 `@media` 断点，不改组件结构，约 0.5 天。若还想有"移动端亮点"，接企业微信/钉钉机器人推送审查完成消息（后端一个 webhook），比做 App 划算得多。

**关于暗色主题与质量大屏**（v1.3 已确认，M6.6 共 2 天）：

- **暗色主题（0.5 天）**：用 Element Plus 内置 dark CSS 变量 + `html.dark` 类切换，偏好存 localStorage。需要额外适配三处——① Monaco 切 `vs-dark`；② ECharts 走统一配色 token，**否则白底图表在暗色页上刺眼**；③ 代码 diff 的红绿底（增/删行）在暗色下要调低一档明度，否则亮得盖住代码。
- **轻量大屏（1.5 天）**：`/screen` 单页，CSS `transform: scale()` 按 1920×1080 等比缩放适配任意显示器；数据只走一个聚合接口 `/api/stats/screen`。**不做轮播、不做点击下钻、不做告警动画**——这三项是"完整大屏"的主要成本，约 2 天且对答辩无实际价值。
- **主次关系**：大屏是演示的**点缀**，报告页与沙盘页才是主体。答辩 8 分钟里，大屏停留不要超过 30 秒，它负责"哇"，报告页负责"服"。

| 维度 | 指标/做法 |
|---|---|

- *视觉 2 天*：暗色主题 0.5 + 轻量大屏 1.5（M6.6）——已经"轻量"过一次，再往上加就是无底洞

> **工期站位（务必看清）**：64.5 个工作日 ≈ 13 周**全职投入**。从现在（2026.10 底）到 2027.04 有约 26 个自然周，但毕业班实际投入率通常只有 50%–70%（课程、求职、考试），换算下来**缓冲只剩 3–5 周，不是 9 周**。因此：
>
> - **2027.01 底**必须完成 M5（RAG）。若未完成，直接进降级模式，不要硬撑六项增强。
> - **2027.02 底** M6.5 至少跑到 E1+E2+E3+E6。未到则按 2.3 的顺序砍 E4 → E5。
> - 六项增强是"锦上添花"，**M4 报告页 + E1 沙盘页**才是答辩的命门，任何时候它们优先。

**若时间只剩 7 周**：M6.5 退回 E1/E2/E3（7 天），M6.6 只留暗色主题、砍掉大屏（-1.5 天）；再紧则保 E1+E3（4 天），把 E2 降级为"只做负样本过滤、不做增长曲线"。

**推进原则**：每个里程碑结束必须"可演示"。宁可 M5 的 RAG 砍到最简（只做缺陷库、不做文档库），也不能让报告页在 M7 还是半成品。

## 13. 测试与对比实验方案

### 13.1 功能测试

- 用例来源：第 3 章功能矩阵逐条派生，每条功能 2~3 个用例（正常/异常/权限）

- 输出：测试用例表（论文 6.2 节直接用）

### 13.2 性能测试

| 场景 | 指标 |
|---|---|
| 报告页加载（500 条缺陷） | 首屏 < 1.5s |
| 全量审查（100 个文件） | 总耗时 < 8min |
| 增量审查（10 个文件变更） | 总耗时 < 90s |

## 14. 风险与降级预案

| 风险 | 影响 | 预案 |
|---|---|---|
| LLM 接口不稳定/限流 | 语义引擎跑不通 | 抽象 `LlmClient`，支持 DeepSeek / 通义 / GLM 三家切换；失败自动降级为静态-only 并标记 |
| 大模型 API 费用 | 实验跑不起 | 结果缓存 + 切片去重 + 实验只跑选定样本；预算控制在百元级 |
| SpotBugs 需编译 | 演示卡住 | 默认关闭，PMD 作主引擎（见 6.2） |
| 项目太大审查超时 | 任务失败 | 文件数上限 + 目录白名单 + 超时截断标记 PARTIAL |
| 向量检索效果差 | RAG 成摆设 | 阈值可调 + 提供"检索测试"页面；最差情况退化为纯 Prompt few-shot，不影响主流程 |
| **BGE-M3 首次拉取失败/超慢**（v1.3） | M0 卡住，M5 连带延期 | 模型缓存挂 volume 只下一次；M0 就预热并跑通 `/embed`；备选：临时切阿里 `text-embedding-v3`（同为 1024 维，只改 base-url） |
| **DeepSeek key 失效或余额不足**（v1.3） | 答辩现场语义引擎直接不可用 | 演示前 24h 跑一次真实调用验证余额；准备第二个 key；`LlmClient` 支持切通义/GLM 兜底 |
| **暗色主题/大屏占用超时**（v1.3） | 挤占 E4/E5/E6 | **硬性 2 天封顶**：超时先砍大屏（1.5 天），只留暗色主题；大屏永远排在六项增强之后 |
| 时间不足 | 做不完 | P1/P2 功能按里程碑砍，P0 九项是底线；增强项按 E4→E5→E6 降级（见 2.3） |

### 16.1 三项由决策衍生的硬约束

**① Key 安全**：`.env` 进 `.gitignore`，仓库只提交 `.env.example`（值为空）。答辩录屏时注意：命令行回显、`docker inspect`、`printenv` 都会暴露环境变量，截图前先清屏。

**② BGE-M3 与库表维度必须锁死**：`knowledge_chunk.embedding`、`defect_kb.embedding` 均为 `vector(1024)`。若换模型（例如换成 768 维的 bge-base），**必须同时改表结构并重建索引**，不能只换服务不改表——"维度不匹配"这类报错在答辩现场极难解释清楚。

**③ "默认关闭"不等于不演示**：准备一个**可编译的小项目**作为开启 SpotBugs 的演示样本，证明它真能跑，而不只是配置里有个开关。这同时回答了"为什么默认关它"——真实项目经常编译不过。

### 16.2 BGE-M3 落地检查清单（M0 阶段逐项打勾）

- [ ] 模型拉取成功（`BAAI/bge-m3`，约 2.2GB），缓存目录挂 Docker volume，避免重启重下
- [ ] `POST /embed` 返回 **1024 维**，维度断言写进健康检查
- [ ] 批量接口可用（一次 32 条），500 条片段入库 < 3 分钟
- [ ] 归一化策略统一：服务端做 L2 归一化 + pgvector 用 `<=>` 余弦距离，**两者不要混用**
- [ ] 启动顺序：`embedding` 先于 `backend`，配 `depends_on` + healthcheck
- [ ] **断网后检索仍可用**（这才能证明"本地部署"不是噱头）

> 这 6 条过不了，M5 的 RAG 会直接卡住。所以**在 M0 就把 embedding 服务跑通**，不要等到 M5 才发现模型有问题。
